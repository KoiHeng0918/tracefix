## 1. 项目背景与目标

### 1.1 背景
Java 初学者在学习和开发中反复遇到两类问题：
1. 概念性问题（如 Bean 生命周期、Redis 缓存击穿），搜索引擎结果质量参差，通用大模型回答缺乏针对性、可能过时或编造。
2. 报错排查（如 `NullPointerException`、`ClassNotFoundException`、连接超时），新手不会读堆栈，定位耗时长。

### 1.2 项目目标
做一个面向 Java 学习者的**知识问答 + 报错诊断 Agent**，回答基于自建知识库（RAG），并给出引用来源，降低幻觉。

### 1.3 成功标准（项目自身，非虚构数据）
- 核心链路可用：文档入库 → 向量化 → 提问 → 检索 → 生成 → 留痕，全流程跑通。
- 有在线演示地址与 GitHub 仓库。
- 沉淀一套 20–30 条的评测集，可量化回答质量（命中率、引用正确率）。
- 所有性能/使用数据来自真实埋点，禁止编造。

|---|---|---|

## 3. 名词解释（面试要能用自己的话解释）

- **RAG（Retrieval-Augmented Generation）**：先从知识库检索相关片段，再把片段连同问题一起交给大模型生成答案，让模型"开卷考试"，区别于让模型凭参数记忆回答。
- **Embedding（向量化）**：把文本转成高维浮点向量，语义相近的文本向量距离近。
- **向量检索**：用问题向量在向量索引中找距离最近的片段（本项目用 FAISS）。
- **混合检索**：向量检索（擅长语义）+ 全文检索（擅长精确关键词，如类名、错误码），再用 RRF 融合排序。
- **RRF（Reciprocal Rank Fusion）**：一种不依赖分数绝对值、只看各榜单排名的融合方法，公式 `score = Σ 1/(k+rank)`，k 常取 60。
- **Agent**：由大模型驱动、能根据任务选择工具/决定流程的程序，本项目用 LangGraph 编排"检索→判断→生成/兜底"的状态流。

## 4. 功能范围与优先级

### P0（MVP，必须完成）
1. 知识文档录入（单条表单 + Markdown/文本文件）
2. 文档异步向量化入库（RabbitMQ 链路，含状态流转与失败重试）
3. 知识问答：混合检索 + RAG 生成 + 引用来源展示
4. 报错诊断：识别异常类型 → 检索相似案例 → 结构化输出（原因/排查/修复）
5. 问答留痕与基础统计（请求量、命中率、耗时）

### P1（有余力再做）
6. 多轮会话（按 session_id 维护上下文）
7. 答案反馈（点赞/点踩），用于筛选坏案例
8. 管理后台：文档状态管理、统计看板

### P2（不影响求职，可不做）
9. 轻量用户体系
10. 评测集自动回归面板

## 6. 技术架构与选型

### 6.1 架构总览
```
浏览器(单页 HTML)
   │  HTTP
Java Spring Boot（主系统：接口/业务/数据/管理）
   │            │                │
   │ HTTP       │ AMQP           │ JDBC
Python FastAPI  │                 MySQL（业务数据）
(AI 引擎)       ├─> RabbitMQ ─> Python 消费(向量化)
  ├ RAG/Agent   │
  ├ FAISS(向量) │
  └ LLM 调用    └─> Redis（缓存/限流/计数）
```

### 6.2 选型与理由（面试高频）

| 选型 | 理由 | 被否方案 |
|---|---|---|
| Java 主 + Python AI 子服务 | Java 是本人主力且承载工程化；AI 生态（LangChain/LangGraph/FAISS）在 Python 侧成熟，两服务 HTTP 解耦 | Spring AI（未学习，不引入）；全 Python（放弃 Java 优势） |
| MySQL + FAISS | 业务数据归 MySQL；向量索引在 Python 侧以本地文件存在，零新增服务 | pgvector（想用熟 MySQL，且不额外部署 PG） |
| 通义 embedding + DeepSeek 生成 | DeepSeek 无 embedding 接口；生成用 DeepSeek 性价比高 | 单厂商（能力缺失） |
| RabbitMQ 异步向量化 | 向量化耗时且依赖外部接口，异步化避免阻塞、支持削峰与重试 | 同步调用（长连接易超时） |

## 7. 数据模型设计

### 7.1 设计方法：从业务流程倒推
1. 列出系统事件：录入文档、向量化（可能失败）、提问、生成回答、统计。
2. 名词归类：文档是"静态资源"，问答是"行为事件" → 两张表，职责分离。
3. 一个文档会被多次问答命中，是一对多关系，不合并。

### 7.2 qa_document（知识文档表）
| 字段 | 类型 | 为什么存在 |
|---|---|---|
| id | BIGINT AUTO_INCREMENT | 主键，用 BIGINT 防自增溢出 |
| title | VARCHAR(200) | 管理展示与检索 |
| category | VARCHAR(50) | 分类（spring/redis/errors…），筛选与分区管理 |
| source | VARCHAR(200) | 出处，支持版权与可信度追溯 |
| content | MEDIUMTEXT | 原文；MEDIUMTEXT 上限 16MB，避免 TEXT 64KB 不够 |
| chunk_count | INT | 向量化切分块数，Python 回调写入，验证处理结果 |
| status | VARCHAR(20) | 异步状态机：PENDING/PROCESSING/DONE/FAILED |
| create_time / update_time | DATETIME | 排查与管理，update_time 自动更新 |

### 7.3 qa_question_log（问答记录表）
| 字段 | 类型 | 为什么存在 |
|---|---|---|
| id | BIGINT | 主键 |
| session_id | VARCHAR(64) | 聚合多轮对话、拉取历史 |
| question | TEXT | 留痕，构成评测坏案例来源 |
| answer | MEDIUMTEXT | 留痕 |
| mode | VARCHAR(20) | CHAT/DIAGNOSE，分类统计 |
| hit_knowledge | TINYINT(1) | 0/1，计算知识库命中率的分子分母 |
| doc_ids | VARCHAR(200) | 命中文档 ID，答案可追溯，校验引用 |
| model | VARCHAR(50) | 换模型后区分数据口径 |
| latency_ms | INT | 性能指标，计算 P50/P95 |
| create_time | DATETIME | 按时间统计 |

### 7.4 索引设计
- `idx_category_status(category, status)`：管理页最高频查询。
- `idx_session(session_id)`：拉取会话历史。
- `idx_create_time(create_time)`：时间区间统计。
- 日志表不建物理外键：高写入、弱关联、文档可能被删，关联在应用层保证。

### 7.5 建表脚本
见 `server/sql/schema.sql`，与本 PRD 字段保持一致，修改需同步两处。

## 9. 异步链路设计（RabbitMQ）

### 9.1 文档向量化流程
1. Java 写入 qa_document（status=PENDING），发送消息（含文档 ID）。
2. Python 消费者收到，回调 Java 将 status 改 PROCESSING。
3. Python 切分 → 调通义 embedding → 写 FAISS。
4. 成功回调 DONE + chunk_count；失败回调 FAILED，支持重试。

### 9.2 可靠性设计（面试重点）
- **消息丢失**：生产者确认（confirm）、队列持久化、消费者手动 ack。
- **重复消费**：以文档 ID 做幂等键，重复消息直接跳过。
- **消费失败**：有限次重试后进入死信，人工在后台重放。

## 10. 埋点与量化指标体系

| 指标 | 来源 | 计算方式 |
|---|---|---|
| 问答/诊断请求量 | qa_question_log | 按 mode、时间计数 |
| 知识库命中率 | hit_knowledge | 命中数 / 总请求数 |
| 响应耗时 P50/P95 | latency_ms | 按时间窗口排序计算 |
| 引用正确率 | 评测集人工标注 | 引用正确条数 / 评测条数 |
| 文档处理成功率 | qa_document.status | DONE 数 / 总文档数 |

没有真实用户前，以"本人 + 评测集"产生真实数据，简历写"目标/可采集指标"，不写虚构用户量。

## 12. 面试拷打情景题（含回答要点）

### 12.1 RAG 与架构
**Q：为什么用 RAG，不直接问大模型或微调？**
A：直接问模型知识会过时、会幻觉且无法溯源；微调成本高、更新知识要重训，不适合频繁变动的知识库。RAG 只更新知识库即可，答案带引用，可解释、成本低。

**Q：Python 服务挂了怎么办？**
A：Java 侧设 HTTP 超时与降级，返回"服务繁忙/稍后再试"，主站与数据库不受影响；记录失败日志用于排查；问答可先落库待恢复。

### 12.2 检索与效果
**Q：为什么向量检索还要加全文检索？**
A：向量检索擅长语义相近但精确关键词弱（如具体类名、错误码、版本号）；全文检索擅长精确匹配。用 RRF 按排名融合，兼顾两类需求。

**Q：怎么减少幻觉？**
A：强制基于检索片段生成、要求输出引用；检索为空时走兜底话术而非硬答；用评测集回归验证引用正确率。

### 12.3 消息队列
**Q：消息重复消费怎么办？**
A：以文档 ID 为幂等键，处理前检查状态，已 DONE 的消息直接 ack 跳过，保证多次消费结果一致。

**Q：文档更新后向量索引怎么同步？**
A：更新文档时旧向量按文档 ID 从 FAISS 删除，重新走一遍向量化链路，状态机保证可追踪。

### 12.4 数据与安全
**Q：这些表为什么这样拆？**
A：按"资源"和"行为事件"拆分，生命周期和读写模式不同；日志表高写入不建外键，文档表强状态管理。

**Q：怎么防 Prompt 注入？**
A：限制输入长度、系统提示词中明确用户输入不可作为指令、对输出做引用约束；知识库内容只收录可信来源。

### 12.5 项目深度
**Q：这个项目最难的部分是什么？**
A：（按真实开发填写，候选）异步链路的幂等与状态一致性、混合检索的融合调参、诊断 Agent 的流程编排。结合一个真实踩坑讲，不要背概念。
