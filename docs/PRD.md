## 0. 版本摘要（先看这一页）

### 0.1 一句话产品

**把一条真实 Java 报错，变成一张有证据、可人工确认、可沉淀复用的诊断工单。**

### 0.2 这次改了什么

| 项目 | v1.0 | v2.0 |
|---|---|---|
| 产品定位 | Java 知识问答 + 报错诊断 | **只做报错诊断**，问答降级为诊断的辅助证据 |
| 核心资产 | 文档知识库 | **结构化报错案例库 + 黄金评测集** |
| 主要交互 | 聊天窗口 | **诊断工单 + 人工确认 + 案例回流** |
| 效果证明 | 20–30 条评测集 | **60 条黄金集，分 dev/test/holdout，CI 自动回归** |
| RAG 的角色 | 产品核心 | **证据检索层**，不是产品本身；无证据必须 abstain |
| 业务闭环 | 回答完即结束 | **提交 → 诊断 → 人工确认 → 修复/升级 → 案例入库 → 评测回归** |

### 0.3 明确不做什么

- 不做通用 Java 知识问答、面试题背诵、代码生成。
- 不做自动改代码、自动执行修复命令、自动关闭工单。
- 不做多语言、多租户、复杂权限体系。
- 不为了用 RAG/MQ/Redis 而增加链路；每个组件必须对应一个真实问题。

## 1. 背景与问题定义

### 1.1 真实痛点

Java 学习者和初级开发者在报错时，通常经历以下过程：

1. 看到一屏堆栈，不知道哪一行才是自己的代码。
2. 把整段报错丢给搜索引擎，得到大量相似但不匹配的答案。
3. 把报错丢给通用大模型，得到“看起来合理”的解释，但无法确认是否适用于自己的版本、框架和上下文。
4. 问题解决后，经验留在聊天记录里，下次遇到同类报错还要重新查。
5. 团队/学习小组里重复踩同一个坑，没有人把“报错—原因—修复—验证”沉淀下来。

通用大模型可以回答“什么是 NullPointerException”，但很难稳定解决“**我这条 Spring Boot + MyBatis-Plus 的报错，根因是什么，依据是什么，改完怎么验证**”。后者需要：

- 对堆栈的精确解析（异常类型、Caused by 链、项目帧 vs 框架帧、错误码）。
- 对相似历史案例的检索与比对。
- 对答案的证据约束和不确定性表达。
- 对“是否真的修好”的人工确认与回流。

### 1.2 为什么选“报错诊断”这个垂直场景

| 维度 | 说明 |
|---|---|
| 高频 | Java 学习者每天都在遇到报错，重复率高 |
| 有客观 ground truth | 修没修好、根因对不对，可以由人确认 |
| 数据可积累 | 每条真实解决过的报错都能变成结构化案例 |
| 通用模型难替代 | 需要私有案例、版本上下文、精确匹配和可追溯证据 |
| 闭环清晰 | 诊断结果可以进入工单，人工确认后沉淀，形成数据飞轮 |

### 1.3 为什么不是“通用 Java 问答”

通用 Java 概念问答已经被通用大模型和搜索引擎覆盖得很好，做出来很难证明价值，也容易被替代。报错诊断的不同点在于：

- 输入是具体的、带上下文的、可验证的。
- 输出需要引用证据，而不是泛泛而谈。
- 结果可以进入真实工作流（工单、确认、复盘）。
- 每次人工确认都在产生独家数据资产。

**结论：RAG 是手段，不是产品；案例数据和工单闭环才是护城河。**

## 2. 产品目标与成功标准

### 2.1 产品目标

1. 让用户把一条报错粘贴进来后，在 1 次交互内得到：异常类型、最可能的根因、可执行的排查/修复步骤、证据来源、需要补充的信息。
2. 让每一次诊断都进入工单，由人工确认根因和修复效果，避免“AI 说完就结束”。
3. 让确认有效的案例回流到案例库，形成“越用越准”的数据资产。
4. 用黄金评测集和 CI 证明效果，而不是凭感觉。

### 2.2 成功标准（目标，不是已达成数据）

| 维度 | 目标 | 采集方式 |
|---|---|---|
| 核心链路 | 真实报错可完成“提交 → 诊断 → 确认 → 修复/升级 → 案例回流” | 工单记录 + 演示录屏 |
| 诊断覆盖 | 黄金集 60 条，覆盖 9 类高频报错 | `eval/golden/` + 覆盖率矩阵 |
| 检索质量 | Recall@5 ≥ 0.85，MRR@10 ≥ 0.70 | 评测脚本（首轮基线后校准） |
| 诊断质量 | 异常类型准确率 ≥ 0.95，根因准确率 ≥ 0.75 | 规则校验 + 人工/LLM 评审 |
| 忠实度 | 引用正确率 ≥ 0.90，无依据断言率 ≤ 0.05 | 引用校验 + 人工抽检 |
| 不确定性 | 信息不足/无证据场景的 abstain 准确率 ≥ 0.80 | 黄金集负例 |
| 工单闭环 | 诊断确认率、解决率、案例回流数可统计 | 工单表 |
| 性能 | 诊断接口 P95 ≤ 8s；检索 ≤ 500ms | `latency_ms` 埋点 |
| 成本 | 单次诊断目标 ≤ ¥0.05；月度 API 预算 100–300 元 | 账单 + 调用量 |

> 以上是**目标阈值**。首轮评测跑完后，根据真实基线调整；任何对外表述都必须写“目标/实测”，不能把目标写成已达成。

### 2.3 初始用户

- 第一用户：本人，用自己真实遇到的报错验证闭环。
- 第二用户（可选）：学习小组/同学，用来验证“别人粘贴的报错”是否也能诊断。
- 不虚构企业用户、日活、并发量；需要时写“目标用户画像”，不写虚假数据。

## 3. 用户与核心场景

### 3.1 角色

| 角色 | 说明 | 主要动作 |
|---|---|---|
| 提交者（Developer） | 被报错卡住的 Java 学习者/初级开发者 | 粘贴堆栈、补充上下文、确认修复是否有效 |
| 确认者/值班人（Maintainer） | 本人或学习小组负责人 | 审核 AI 根因、确认/驳回、决定升级 |
| 案例管理员（Curator） | 本人 | 把已解决工单整理成案例卡、审核入库、维护评测集 |

> 个人项目中，三个角色可以由本人一人扮演；但流程和状态必须分开设计，方便面试讲清“如果团队使用，谁负责哪一步”。

### 3.2 核心场景

#### 场景 A：已知报错，快速命中

用户粘贴 `java.lang.NullPointerException: Cannot invoke "com.xxx.User.getName()" because "user" is null`，并补充是 Spring Boot 3.x + MyBatis-Plus。

系统：

1. 抽取异常类型、消息、项目帧。
2. 指纹命中案例 `ERR-SPRING-0007`。
3. 输出根因假设、证据引用、3 步修复、验证方式。
4. 创建工单，状态 `DIAGNOSED`。
5. 用户确认“根因正确、修复有效”，工单 `RESOLVED`，生成案例候选。

#### 场景 B：信息不足，先追问

用户只粘贴 `Application run failed`，没有完整堆栈、没有版本。

系统不硬答，返回 `NEED_INFO`，明确列出需要补充：

- 完整堆栈（含 Caused by）；
- JDK / Spring Boot / 依赖版本；
- 相关配置或代码片段；
- 报错前做了什么改动。

#### 场景 C：没有相似案例，明确 abstain

用户粘贴一个极冷门的自定义异常，案例库无相似项。

系统返回 `ABSTAINED`：

- 说明“当前案例库没有足够证据”；
- 给出通用的排查方向，但标注为“非案例证据”；
- 建议升级人工/GitHub Issue；
- 不编造根因，不伪造引用。

#### 场景 D：AI 诊断错误，人工驳回

用户确认“根因不对”，填写实际原因。

系统：

- 工单 `REJECTED`；
- 记录负例（错误诊断 + 人工纠正）；
- 该负例进入评测/案例改进队列，不直接污染案例库。

#### 场景 E：修复有效，沉淀案例

工单 `RESOLVED` 后，系统生成案例草稿：

- 从工单带入报错、上下文、确认后的根因、修复步骤、验证方式；
- 人工补充标题、分类、版本范围、来源；
- 审核通过后 `ACTIVE`，写入 MySQL，重建/增量更新 FAISS；
- 可加入黄金集候选（需标注预期行为）。

## 4. 产品原则

1. **证据优先**：每个根因结论必须能指向案例证据；无证据就 abstain/ask。
2. **人工在环**：AI 产出“待确认诊断”，人工确认根因和修复效果；AI 不自动关闭工单。
3. **垂直优先**：只做报错诊断；通用问答、代码生成不做。
4. **数据飞轮**：每次确认/驳回都产生标注数据；有效案例回流，无效案例成为负例。
5. **可评测**：没有黄金集和指标，不称“效果好”。
6. **最小闭环**：先跑通一条报错的完整闭环，再扩分类、扩功能。
7. **可解释**：本人能讲清每个模块为什么存在；讲不清的抽象不加。
8. **不滥用组件**：RAG、MQ、Redis 只在解决具体问题时使用。

### 4.1 什么时候不用 RAG

- 指纹精确命中高质量案例：直接返回案例，LLM 只负责组织语言和补充验证步骤。
- 输入信息不足：直接 `NEED_INFO`，不调用昂贵生成。
- 案例库无证据：直接 `ABSTAINED`，不硬答。
- 用户问纯概念题：引导到通用助手/文档，不在本项目主链路里做。

### 4.2 为什么仍然需要检索

报错文本包含大量精确信号（异常类名、错误码、SQLState、框架包名），也包含语义信号（“启动时 Bean 找不到”）。因此需要：

- 精确匹配：异常类型、消息模式、错误码、堆栈帧；
- 语义匹配：现象描述不同但根因相同；
- 元数据过滤：技术栈、版本、分类；
- 融合排序：RRF + 规则重排。

检索是“找证据”，不是“为了显得像 RAG”。

## 6. 业务闭环：AI 给出原因之后怎么办

### 6.1 结论

**AI 自动创建诊断工单，但只给出“待确认诊断”；由人工确认根因和修复效果。确认有效 → 工单解决 → 案例回流；确认无效 → 驳回/升级。AI 不自动关闭工单，不自动改代码。**

选择“人工确认 + 自动建单”，而不是“AI 自动处理”，原因：

1. 报错诊断存在版本、环境、业务上下文差异，AI 不能承担错误结论的后果。
2. 人工确认是最有价值的标注信号，是数据飞轮的入口。
3. 个人项目没有真实值班团队，人工确认可以由本人完成；流程设计与团队使用一致，面试可讲清角色分离。
4. 自动建单保证每次诊断都留痕，避免“聊完就丢”。

### 6.2 工单状态机

```
SUBMITTED
   │ AI 诊断完成
   ├─→ DIAGNOSED ──人工确认根因正确──→ CONFIRMED ──修复有效──→ RESOLVED ──→ ARCHIVED
   │        │                              │
   │        └─人工驳回──────────────────→ REJECTED
   │
   ├─→ NEED_INFO ──用户补充──→ SUBMITTED（同一工单）
   ├─→ ABSTAINED ──人工升级──→ ESCALATED
   └─→ DIAGNOSIS_FAILED ──重试/人工──→ SUBMITTED 或 ESCALATED
```

| 状态 | 触发者 | 含义 | 允许的下一步 |
|---|---|---|---|
| `SUBMITTED` | 系统/用户 | 工单已创建，等待诊断 | `DIAGNOSED` / `NEED_INFO` / `ABSTAINED` / `DIAGNOSIS_FAILED` |
| `DIAGNOSED` | AI | 已给出带证据的诊断 | `CONFIRMED` / `REJECTED` |
| `NEED_INFO` | AI | 信息不足，需补充 | `SUBMITTED` |
| `ABSTAINED` | AI | 无足够证据，拒绝硬答 | `ESCALATED` / `SUBMITTED`（补充后） |
| `CONFIRMED` | 人工 | 根因确认正确 | `RESOLVED` / `ESCALATED` |
| `REJECTED` | 人工 | 根因不正确 | `ESCALATED` / `ARCHIVED`（作为负例） |
| `RESOLVED` | 人工 | 修复有效，问题解决 | `ARCHIVED` |
| `ESCALATED` | 人工/系统 | 转人工或外部 Issue | `RESOLVED` / `ARCHIVED` |
| `ARCHIVED` | 人工/系统 | 工单关闭；可生成案例草稿 | 结束 |
| `DIAGNOSIS_FAILED` | 系统 | AI 服务异常/超时 | `SUBMITTED`（重试）/ `ESCALATED` |

规则：

- AI 只能推进到 `DIAGNOSED` / `NEED_INFO` / `ABSTAINED`，不能写 `CONFIRMED` / `RESOLVED`。
- `RESOLVED` 必须有人工确认的 `fix_effective = true` 和解决说明。
- `ARCHIVED` 不自动等于“案例已入库”；案例入库需要单独审核。
- 低置信度、生产环境、数据丢失/安全相关报错，优先 `NEED_INFO` 或 `ESCALATED`，不给高风险自动建议。

### 6.3 案例回流流程

```
RESOLVED 工单
  → 系统生成案例草稿（带 source_ticket_id）
  → 人工补充/修正：标题、分类、异常类型、消息模式、版本范围、根因、修复、验证、来源
  → 指纹去重：与现有案例重复则合并/拒绝
  → 质量审核（可复现、根因具体、修复已验证、无敏感信息）
  → qa_error_case.status = ACTIVE
  → 更新 FAISS 索引
  → 可选：加入黄金集候选（需标注 split 和预期行为）
```

关键约束：

- 不是每个 `RESOLVED` 都自动入库；必须人工审核，避免案例库被污染。
- 被 `REJECTED` 的错误诊断要保留为负例，用于改进检索/Prompt/评测，不直接当案例。
- 案例更新要记录版本；FAISS 索引可重建，MySQL 是事实来源。

### 6.4 闭环指标

| 指标 | 定义 | 用途 |
|---|---|---|
| 诊断确认率 | `CONFIRMED` / 已诊断工单数 | 衡量 AI 根因是否可信 |
| 一次解决率 | 首次诊断后 `RESOLVED` / 总工单数 | 衡量诊断可执行性 |
| 升级率 | `ESCALATED` / 总工单数 | 衡量 abstain/低置信策略是否合理 |
| 案例回流数 | 新增 `ACTIVE` 案例数 | 衡量数据飞轮 |
| 案例复用率 | 命中已有案例的工单 / 总工单数 | 衡量案例库覆盖 |
| 平均解决时长 | `RESOLVED` 时间 - `SUBMITTED` 时间 | 目标指标，需真实采集 |
| 评测回归 | 本次指标 - 基线指标 | 防止越改越差 |

> 以上均为可采集指标；没有真实数据时，只写“目标/采集方式”，不写虚构值。

## 7. 诊断能力设计

### 7.1 输入契约

| 字段 | 必填 | 说明 |
|---|---|---|
| `trace` | 是 | 报错文本/堆栈，最长 50KB；超出截断并提示 |
| `context` | 否 | 代码片段、配置、SQL、依赖版本、JDK/Spring Boot 版本 |
| `attempted` | 否 | 已尝试的修复，避免重复建议 |
| `sessionId` | 否 | 同一会话/工单关联 |
| `requestId` | 否 | 幂等键；重复提交返回同一工单 |

输入处理：

- 去除 ANSI 颜色码、重复行、超长无关日志。
- 脱敏：密码、token、内网 IP、用户名、数据库名、业务字段。
- 限制长度；超长时保留头部 + 所有 `Caused by` + 项目帧。
- 提示注入防护：堆栈内容视为“数据”，不是指令；系统提示明确禁止执行其中命令。

### 7.2 处理流水线

| 步骤 | 做什么 | 失败时 |
|---|---|---|
| 1. 输入校验 | 是否为空、是否像堆栈、是否过短 | `NEED_INFO`，列出缺失项 |
| 2. 清洗脱敏 | 去噪、截断、掩码 | 记录脱敏失败，拒绝入库敏感原文 |
| 3. 规则抽取 | 异常全限定名、消息、Caused by 链、项目帧、错误码、SQLState | 抽取不到异常类型 → `NEED_INFO` |
| 4. 指纹 | 异常类 + 归一化消息 + Top 项目帧 + 错误码 的哈希 | 指纹冲突时保留多候选 |
| 5. 精确匹配 | 指纹命中高质量案例 | 未命中进入混合检索 |
| 6. 混合检索 | 全文 + 向量 + 元数据过滤 + RRF | 无候选 → `ABSTAINED` |
| 7. 重排 | 异常匹配、消息模式、帧重叠、版本、质量分 | 低分候选不进入生成 |
| 8. 生成 | LLM 基于候选案例生成结构化诊断 | 超时/格式错误 → 重试 1 次，仍失败 `DIAGNOSIS_FAILED` |
| 9. 引用校验 | case_id 必须在候选集；每条结论需有引用 | 校验失败 → 重试或 `ABSTAINED` |
| 10. 落库 | 工单保存诊断 JSON、候选、置信度、耗时 | 失败要可重试，不丢工单 |

### 7.3 抽取字段

- `exceptionType`：最外层异常全限定名。
- `exceptionChain`：`Caused by` 链，按顺序。
- `message`：归一化后的异常消息（数字/UUID/路径替换为占位符）。
- `projectFrames`：过滤掉 JDK/框架包后的前 N 个项目帧。
- `frameworkFrames`：Spring/MyBatis/Netty 等关键框架帧。
- `errorCode` / `sqlState` / `httpStatus`：如存在。
- `fingerprint`：SHA-256（异常类 + 归一化消息 + Top 3 项目帧 + 错误码）。
- `missingInfo`：缺失的关键上下文（版本、完整堆栈、SQL、配置）。

### 7.4 检索设计

**候选来源：**

1. 指纹精确匹配：最高优先级。
2. 全文/BM25：异常类名、消息模式、错误码、SQLState、关键帧。
3. 向量检索：现象、根因、修复步骤的语义相似。
4. 元数据过滤：分类、技术栈、版本范围、案例状态 `ACTIVE`。

**融合：**

- RRF，`k = 60`，融合多路排名。
- 取 Top 20 进入重排，重排后取 Top 5 作为生成证据。

**重排特征（初始权重，后续用 dev 集调）：**

| 特征 | 初始权重 | 说明 |
|---|---|---|
| 异常类型完全匹配 | 0.35 | 最强信号 |
| 消息模式匹配 | 0.25 | 归一化后的模式 |
| 项目帧重叠 | 0.15 | Top 帧 Jaccard |
| 技术栈/版本匹配 | 0.10 | 避免跨版本误配 |
| 分类匹配 | 0.10 | Spring/MyBatis/MySQL 等 |
| 案例质量分 | 0.05 | 人工审核质量 |

> 权重不是永久真理；必须用 dev 集调，test/holdout 只用于验证。

### 7.5 结构化输出

```json
{
  "summary": "一句话结论",
  "exception": {
    "type": "java.lang.NullPointerException",
    "message": "Cannot invoke ... because ... is null",
    "chain": ["java.lang.NullPointerException"]
  },
  "rootCauses": [
    {
      "rank": 1,
      "cause": "User 对象未初始化，Service 直接调用 getName()",
      "confidence": 0.82,
      "evidenceCaseIds": ["ERR-SPRING-0007"],
      "evidenceSnippets": ["案例中相同堆栈帧和消息模式"]
    }
  ],
  "diagnosticSteps": [
    "确认 user 的来源：数据库查询、缓存还是外部接口",
    "检查 MyBatis 查询是否返回 null",
    "在调用 getName() 前加空值判断或使用 Optional"
  ],
  "fixSteps": [
    {
      "step": 1,
      "action": "在 Service 层对查询结果做空值校验",
      "why": "避免对 null 调用方法",
      "risk": "low"
    }
  ],
  "verification": [
    "用相同入参复现，确认不再抛 NPE",
    "补充单测覆盖 user 为 null 的分支"
  ],
  "missingInfo": [],
  "riskNotes": [],
  "citations": [
    {
      "caseId": "ERR-SPRING-0007",
      "title": "MyBatis 查询结果为 null 导致 NPE",
      "supports": "根因与修复步骤"
    }
  ],
  "confidence": 0.82,
  "nextAction": "CONFIRM_OR_ESCALATE"
}
```

约束：

- `citations[].caseId` 必须来自本次检索候选集；后端/服务端做白名单校验。
- `rootCauses[].cause` 必须能对应至少一条 citation；无引用不得作为确定结论。
- `missingInfo` 非空时，`nextAction` 应为 `ASK_FOR_INFO`。
- 不输出“执行以下命令”这类高风险动作；修复建议只做描述，不自动执行。
- 输出 JSON 必须通过 schema 校验；失败重试 1 次，仍失败则降级。

### 7.6 置信度与 abstain

| 情况 | 判定 | 输出 |
|---|---|---|
| 指纹精确命中高质量案例，重排分高 | 高置信 | `DIAGNOSED`，正常给出根因/修复 |
| 有相似案例，但版本/堆栈不完全匹配 | 中置信 | `DIAGNOSED` + 明确“待确认”，列出差异点 |
| 候选分低、证据弱、关键信息缺失 | 低置信 | `NEED_INFO`，列出需要补充的 3–5 项 |
| 无候选或引用校验失败 | 无证据 | `ABSTAINED`，说明原因，建议升级 |
| 生产/数据丢失/安全相关 | 高风险 | 不自动下结论，`NEED_INFO` 或 `ESCALATED` |

具体阈值（初始目标，需用 dev 集校准）：

- `confidence ≥ 0.75` 且至少 1 条高质量证据 → 正常诊断。
- `0.45 ≤ confidence < 0.75` → 给出假设，但必须标注不确定性，并建议人工确认。
- `confidence < 0.45` 或无有效引用 → `NEED_INFO` / `ABSTAINED`。

### 7.7 为什么不是“纯 LLM 问答”

| 纯 LLM | 本项目 |
|---|---|
| 依赖参数记忆，可能过时/编造 | 基于案例证据，带引用 |
| 对精确错误码/版本不稳定 | 规则抽取 + 精确匹配 + 元数据过滤 |
| 没有业务闭环 | 工单、人工确认、案例回流 |
| 效果靠感觉 | 黄金集 + CI 指标 |
| 每次回答互不相关 | 指纹去重、案例复用、负例积累 |

### 7.8 为什么不是“纯规则系统”

纯规则无法覆盖自然语言描述、跨版本差异和多根因排序；LLM 适合在**有证据约束**的前提下做归纳、解释和步骤组织。规则负责“确定性”，LLM 负责“表达与归纳”，两者结合。

## 8. 数据资产：报错案例库

### 8.1 案例卡 schema

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | BIGINT | 是 | 主键 |
| `case_no` | VARCHAR(32) | 是 | 业务编号，如 `ERR-SPRING-0007`，唯一 |
| `title` | VARCHAR(200) | 是 | 一句话描述现象 |

| `message_pattern` | VARCHAR(500) | 是 | 归一化消息模式/正则 |
| `tech_stack` | VARCHAR(100) | 是 | Spring Boot 3.x + MyBatis-Plus 3.5.x 等 |
| `version_scope` | VARCHAR(100) | 否 | 适用版本范围；不确定写“未验证” |
| `symptom` | TEXT | 是 | 用户看到的现象/堆栈摘要 |
| `root_cause` | TEXT | 是 | 具体根因，不写“配置问题”这种空话 |
| `fix_steps` | TEXT/JSON | 是 | 有序修复步骤 |
| `verification` | TEXT | 是 | 怎么确认修好 |
| `source` | VARCHAR(200) | 是 | 自己项目/公开 issue/官方文档 |
| `source_url` | VARCHAR(500) | 否 | 公开来源链接 |
| `license` | VARCHAR(50) | 否 | 公开来源许可证/使用说明 |
| `fingerprint` | CHAR(64) | 是 | 去重/精确匹配 |
| `embedding_id` | VARCHAR(100) | 否 | FAISS 中的 ID |
| `quality_score` | TINYINT | 是 | 1–5，人工审核 |
| `status` | VARCHAR(20) | 是 | DRAFT/REVIEW/ACTIVE/DEPRECATED |
| `source_ticket_id` | BIGINT | 否 | 从哪张工单回流 |
| `hit_count` | INT | 是 | 被检索命中次数，用于评估价值 |
| `create_time` / `update_time` | DATETIME | 是 | 审计 |

### 8.2 案例质量规则

一条案例只有同时满足以下条件，才能进入 `ACTIVE`：

1. **可复现**：有足够的报错文本/上下文，别人能理解触发条件。
2. **根因具体**：能指出是哪段代码/配置/依赖/数据导致，不写“环境问题”。
3. **修复已验证**：人工确认修复有效，或至少有明确的验证方式。
4. **版本有边界**：标注适用技术栈/版本；不确定就写“未验证”，不要假装通用。
5. **来源可追溯**：自己项目/公开链接/官方文档，注明许可证。
6. **无敏感信息**：密码、token、内网 IP、业务数据已脱敏。
7. **指纹不重复**：与现有案例重复时合并或拒绝。

### 8.3 分类与覆盖矩阵

| 分类 | 典型报错 | 初始案例目标 |
|---|---|---|
| Spring | Bean 找不到、循环依赖、启动失败、事务不生效 | 15 |
| MyBatis / MyBatis-Plus | 绑定异常、SQL 语法、分页插件、映射错误 | 10 |
| MySQL | 连接失败、死锁、慢查询、字段/索引错误 | 10 |
| Redis | 连接超时、序列化、缓存穿透/击穿 | 8 |
| RabbitMQ | 连接失败、消息丢失、重复消费、死信 | 7 |
| JVM | OOM、GC、类加载、栈溢出 | 8 |
| 并发 | 线程池、锁、可见性、死锁 | 6 |
| 构建/部署 | Maven 依赖、JDK 版本、端口、Nginx | 6 |
| 网络 | 超时、DNS、TLS、代理 | 5 |

> 初始目标合计约 75 条案例卡；先做 30–50 条，再按真实使用补齐。黄金集 60 条与案例库不是同一份数据。

### 8.4 数据来源与合规

1. **首选**：本人项目中真实出现的报错，附带真实修复过程。
2. **次选**：公开 issue / Stack Overflow / 官方文档中的典型案例，逐条整理，注明链接和许可证。
3. **禁止**：整站抓取、未脱敏的内部数据、无法确认来源的“网上抄来的答案”。
4. 公开案例只保留理解问题所需的最短堆栈，不复制大段受版权保护的正文。
5. 提供删除/更正机制：发现来源或内容有问题，标记 `DEPRECATED` 并重建索引。

### 8.5 案例库 vs 黄金集

| | 案例库 | 黄金集 |
|---|---|---|
| 目的 | 给诊断提供证据 | 给效果提供考卷 |
| 内容 | 尽可能全的 ACTIVE 案例 | 有标准答案的 60 条场景 |
| 是否可被检索 | 是 | 不直接作为检索语料（可引用案例 ID） |
| 是否可调参 | 可以增删改 | dev 可调；test 谨慎；holdout 禁止 |
| 污染风险 | 低质量案例会降低诊断 | 标签被改会让指标失真 |

## 9. 评测体系（Golden Dataset + CI）

### 9.1 黄金集 schema

文件：`eval/golden/cases.jsonl`（每行一条）

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 用例编号，如 `G-0001` |
| `split` | 是 | `dev` / `test` / `holdout` |
| `category` | 是 | 与案例库分类一致 |
| `difficulty` | 是 | easy/medium/hard |
| `input_trace` | 是 | 真实报错文本（脱敏） |
| `input_context` | 否 | 代码/版本/配置 |
| `expected_behavior` | 是 | `DIAGNOSE` / `ASK_INFO` / `ABSTAIN` |
| `gold_exception_type` | 条件 | `DIAGNOSE` 时必填 |
| `gold_root_cause` | 条件 | 自由文本，供人工/LLM 评审 |
| `gold_root_cause_tags` | 条件 | 关键词/标签，便于自动匹配 |
| `gold_case_ids` | 条件 | 应命中的案例 ID；无则空数组 |
| `gold_fix_keywords` | 否 | 修复步骤应覆盖的关键动作 |
| `must_not_claim` | 否 | 禁止出现的错误结论/危险建议 |
| `source` | 是 | 自己项目/公开来源/构造 |
| `notes` | 否 | 评审说明 |

### 9.2 数据集构成（60 条）

| 维度 | 拆分 |
|---|---|
| 总量 | 60 |
| 按 split | dev 30 / test 20 / holdout 10 |
| 按难度 | easy 20 / medium 30 / hard 10 |
| 按预期行为 | DIAGNOSE 45 / ASK_INFO 10 / ABSTAIN 5 |
| 按分类 | Spring 15 / MyBatis 10 / MySQL 8 / Redis 6 / MQ 5 / JVM 6 / 并发 4 / 构建部署 4 / 网络 2 |

规则：

- `dev` 用于调 Prompt、检索权重、阈值；`test` 用于 CI 回归；`holdout` 只在里程碑/发版跑。
- 每条用例必须有来源和预期行为；不能全是自己构造的“顺风局”。
- 负例（ASK_INFO/ABSTAIN）至少占 25%，否则系统会学会“什么都敢答”。
- 标签变更写 changelog；`test/holdout` 的标签变更需要复核。

### 9.3 指标定义

| 指标 | 定义 | 适用 | 初始目标 |
|---|---|---|---|
| Recall@5 | 命中 `gold_case_ids` 中任一案例的用例数 / 有 gold_case_ids 的用例数 | 检索 | ≥ 0.85 |
| MRR@10 | 首个正确案例排名倒数的均值 | 检索 | ≥ 0.70 |
| Top-1 Accuracy | 排名第一的案例正确的比例 | 检索 | 报告值 |
| 异常类型准确率 | 抽取的异常类型与 gold 完全一致 / DIAGNOSE 用例 | 解析 | ≥ 0.95 |
| 根因准确率 | 根因要点匹配（标签/人工 rubric ≥ 4/5） / DIAGNOSE 用例 | 诊断 | ≥ 0.75 |
| 引用正确率 | 被引用案例确实支持对应结论的条数 / 总引用条数 | 忠实度 | ≥ 0.90 |
| 答案忠实度 | 有证据支持的断言数 / 总断言数 | 忠实度 | ≥ 0.90 |
| 无依据断言率 | 1 - 忠实度 | 忠实度 | ≤ 0.05 |
| 修复步骤覆盖率 | 命中的 `gold_fix_keywords` / 总关键词 | 可执行性 | 报告值 |
| abstain 准确率 | 正确输出 ASK_INFO/ABSTAIN 的负例数 / 负例总数 | 不确定性 | ≥ 0.80 |
| 误答率 | 负例中被硬答的比例 | 不确定性 | ≤ 0.10 |
| 人工可执行性 | 人工 1–5 分均值 | 产品 | ≥ 4.0（目标） |
| P95 延迟 | 诊断接口 P95 | 性能 | ≤ 8s |
| 单次成本 | 平均 token/费用 | 成本 | ≤ ¥0.05（目标） |

> 指标必须带样本数；60 条是小样本，不做夸张的统计显著性结论。

### 9.4 评测分层与 CI

| 层级 | 触发 | 内容 | 是否调用 LLM | 门禁 |
|---|---|---|---|---|
| L1 快速层 | 每次 PR | 单测 + 检索评测（固定索引、固定案例集） | 否 | Recall@5、MRR 不低于基线 5% |
| L1.5 小样本忠实度（可选） | 每次 PR 或合并前 | 10 条固定诊断样例，优先读缓存 | 是（有预算时） | 引用正确率/abstain 不低于基线 |
| L2 全量层 | 每晚/手动 | test 集完整诊断；规则指标 + LLM judge | 是 | 根因、引用、abstain 不低于基线 |
| L3 发版层 | 里程碑/发版 | holdout + 人工抽检 20% | 是 | 人工评审通过；无严重回归 |

> 成本取舍：L1 必须每次 PR 跑；L1.5 在预算允许时开启，用缓存和固定样例控制成本；L2 夜间跑全量，避免每次 PR 都产生大额 API 费用。这样既满足“每次构建有回归”，又不让评测成本失控。

L1 设计要点：

- 使用冻结的案例索引和脱敏后的 golden 输入，不依赖外部 API。
- 只评检索和解析，快速、稳定、便宜。
- 如果改动了案例库/检索逻辑，必须跑 L1。

L2 设计要点：

- 固定模型版本、temperature=0（或最低）、固定 Prompt 版本。
- 缓存 LLM 结果用于复现，但 Prompt/模型/检索版本变化时使缓存失效。
- 记录每次运行的 JSON + Markdown 报告，和基线对比。
- 预算上限：单次全量评测不超过预设金额；超限停止并报告。

L3 设计要点：

- holdout 不参与调参；只在发版前跑。
- 人工抽检 20%，重点看引用是否真实、修复是否可执行、是否漏掉关键风险。
- 如果 holdout 明显低于 test，说明过拟合，先查数据泄漏/标签问题。

### 9.5 LLM-as-judge 校准

- 用 20 条人工标注样本校准 judge。
- 计算 judge 与人工的一致率；目标 ≥ 80%。
- 未达标时，judge 只作为报告，不作为 CI 门禁；以规则指标 + 人工抽检为准。
- judge 的 rubric 要写清楚：根因是否正确、引用是否支持、修复是否可执行、是否遗漏关键风险。
- 避免让同一个模型“自评自夸”；必要时换模型或人工复核。

### 9.6 防过拟合

1. dev/test/holdout 物理隔离；holdout 文件访问受控。
2. 不在 test 上反复调 Prompt；调参只看 dev。
3. 标签变更记录原因和复核人；禁止为了指标好看改标签。
4. 保留基线报告；每次对比“本次 vs 基线”，而不是只看绝对值。
5. 增加“分布外”用例：新框架版本、少见的 Caused by、信息不足的输入。
6. 报告分类指标，不只看总分；避免某一类被平均掉。

## 10. 技术架构

### 10.1 总览

```
浏览器（单页 HTML）
   │ HTTP
Java Spring Boot 主服务
   │  ├─ 工单/案例/确认/统计（MySQL）
   │  ├─ 输入校验、限流、缓存（Redis）
   │  └─ HTTP 调用 Python AI 服务
   │
Python FastAPI AI 服务
   ├─ 清洗脱敏 / 堆栈解析 / 指纹
   ├─ 混合检索（FAISS + 全文 + 元数据）
   ├─ 重排
   ├─ LLM 结构化生成（DeepSeek）
   └─ 引用校验 / 置信度
   │
MySQL（事实来源） ── FAISS（派生索引，可重建）
   │
RabbitMQ（批量导入/索引重建/评测任务/失败重试）
```

### 10.2 职责边界

| 组件 | 负责 | 不负责 |
|---|---|---|
| Java 主服务 | 工单状态机、案例 CRUD、确认动作、权限（P1）、对外 API、持久化 | 不做堆栈解析/检索/生成 |
| Python AI 服务 | 解析、指纹、检索、重排、Prompt、LLM 调用、引用校验、评测 | 不改工单状态、不直接写业务表（通过 Java 回调/接口） |
| MySQL | 案例、工单、原始资料的事实来源 | 不存向量 |
| FAISS | 向量索引，可重建 | 不作为事实来源 |
| Redis | 缓存、限流、计数 | 不存唯一业务数据 |
| RabbitMQ | 异步任务 | 不用于“为了异步而异步”的主链路 |

### 10.3 同步与异步

- **诊断主链路同步**：用户等待结果，Java 调 Python，超时 10s；失败创建/保留工单，状态 `DIAGNOSIS_FAILED`。
- **案例导入异步**：批量导入/重建索引走 MQ，避免阻塞；单条案例可由管理员同步导入后后台建索引。
- **评测离线**：脚本直接调用 Python 服务或内部诊断函数，不经过前端。
- **失败重试**：P1 用 MQ 重试；P0 允许人工在工单页重试。

### 10.4 降级策略

| 故障 | 行为 |
|---|---|
| Python 服务超时/不可用 | Java 返回“已创建工单，诊断服务暂不可用”，工单保留；P1 自动重试 |
| LLM 超时/限流 | 重试 1 次；仍失败 → `DIAGNOSIS_FAILED`，不伪造答案 |
| FAISS 索引缺失/损坏 | 从 MySQL 重建；重建期间检索降级为全文/精确匹配 |
| 引用校验失败 | 重试 1 次；仍失败 → `ABSTAINED`，不输出无依据结论 |
| Redis 不可用 | 跳过缓存，直接走诊断；不影响正确性 |

### 10.5 缓存

- key：`fingerprint + prompt_version + retrieval_version + model`。
- TTL：短期（如 24h）；案例更新/索引重建时主动失效。
- 缓存只缓存“诊断结果”，不缓存用户敏感原文；缓存值也要脱敏。
- 命中缓存也要记录工单，保证闭环数据完整。

### 10.6 选型理由（面试用）

| 选型 | 理由 | 被否方案 |
|---|---|---|
| Java 主 + Python AI | Java 承载工程/工单；Python 的检索与 LLM 生态成熟；HTTP 解耦 | Spring AI（未学，增加负担）；全 Python（放弃 Java 优势） |
| MySQL + FAISS | 业务数据用熟 MySQL；FAISS 本地文件零新增服务；索引可重建 | pgvector（不想额外部署 PG）；Milvus（过重） |
| 通义 embedding + DeepSeek 生成 | DeepSeek 无 embedding；生成性价比高 | 单厂商（能力缺失） |
| RabbitMQ 只做异步任务 | 批量导入/索引重建/评测确实耗时；诊断主链路要实时 | 全链路 MQ（增加复杂度，用户等待体验差） |
| 单页 HTML | 前端薄弱，先做最小可用页面 | React/Vue 全家桶（学习成本高，偏离主线） |

### 12.2 `POST /diagnosis/analyze`

请求：

```json
{
  "inputTrace": "java.lang.NullPointerException: ...\n\tat com.demo.UserService...",
  "inputContext": "Spring Boot 3.2.0, MyBatis-Plus 3.5.5, JDK17",
  "attempted": "已经检查过数据库连接",
  "sessionId": "s-20261102-001",
  "requestId": "r-001"
}
```

响应：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "ticketId": 1001,
    "ticketNo": "D-20261102-0001",
    "status": "DIAGNOSED",
    "diagnosis": { "summary": "...", "rootCauses": [], "citations": [], "confidence": 0.82 },
    "missingInfo": []
  }
}
```

约束：

- `requestId` 幂等：重复提交返回同一工单。
- 输入超长/为空返回 400，并给出明确提示。
- AI 不可用返回 503，但仍创建工单（状态 `DIAGNOSIS_FAILED`），响应里带 `ticketId`。
- `diagnosis` 必须通过 schema 校验；不合法时不要返回半成品。

### 12.3 `POST /diagnosis/confirm`

请求：

```json
{
  "ticketId": 1001,
  "rootCauseCorrect": true,
  "fixEffective": true,
  "confirmedRootCause": "user 查询结果为 null，Service 未判空",
  "resolutionNote": "在 Service 层加空值校验并补单测"
}
```

响应：返回更新后的工单状态（`RESOLVED` / `CONFIRMED` / `REJECTED`）。

规则：

- 只有人工调用；AI/系统不能直接调用确认接口。
- `fixEffective=true` 且 `resolutionNote` 非空，才允许 `RESOLVED`。
- `rootCauseCorrect=false` 时，`confirmedRootCause` 必填，作为负例。
- 确认后可选触发案例草稿生成（P0 可手动/半自动）。

- `POST /diagnosis/escalate`：`{ticketId, reason}`；P1 可导出 GitHub Issue（脱敏）。

## 13. 前端与交互（最小可用）

### 13.1 页面结构

单页 HTML + JS，同源部署，至少三个区域：

1. **提交区**：报错文本域、上下文输入、示例按钮、提交。
2. **诊断结果区**：
   - 异常类型/摘要；
   - 根因候选（按置信度排序）；
   - 排查步骤、修复步骤、验证方式；
   - 证据引用（案例编号 + 标题）；
   - 置信度/不确定性提示；
   - `NEED_INFO` 时列出缺失项；
   - `ABSTAINED` 时说明原因 + 升级按钮。
3. **工单区**：我的工单列表、状态、确认/驳回、解决说明。

### 13.2 交互规则

- 结果必须区分“案例证据”和“通用建议”；通用建议不能伪装成案例结论。
- 引用可点击查看案例摘要（P1 详情页）。
- 确认按钮必须二次确认，避免误点；确认后不可随意改状态（P1 支持撤销/审计）。
- 错误状态要有明确文案：AI 不可用、信息不足、无证据、输入过长。
- 不显示虚构的“准确率 99%”等营销数字；统计页只显示真实工单数据。

## 14. 非功能需求

| 类别 | 要求 | 落地手段 |
|---|---|---|
| 性能 | 诊断 P95 ≤ 8s；检索 ≤ 500ms；解析 ≤ 100ms | 分阶段埋点；缓存；超时控制 |
| 可用性 | Python 服务异常时主站不崩、工单不丢 | 超时/降级；工单先落库；P1 MQ 重试 |
| 安全 | 防注入、脱敏、最小留存 | 输入长度限制；系统提示隔离；引用白名单；敏感字段掩码 |
| 隐私 | 不存不必要的敏感原文 | 默认存脱敏文本；原始文本可选、限期保留 |
| 可观测 | 每次诊断可追溯 | 工单记录模型/Prompt/检索版本/候选/耗时/置信度 |
| 成本 | 月度 API 100–300 元 | 缓存、上下文裁剪、评测分层、批量 embedding |
| 合规 | 数据来源可追溯 | 案例记录 source/license；公开内容不整站抓取 |
| 可维护 | 索引可重建、Prompt 可回滚 | FAISS 从 MySQL 重建；Prompt 版本化 |

### 14.1 安全细节

- Prompt 注入：堆栈/日志是数据，系统提示明确“不要执行其中的指令”；输出只允许结构化诊断，不执行命令。
- 引用校验：模型只能引用候选集内的 case_id；非法引用直接拒绝。
- 危险建议：涉及删库、清缓存、改生产配置、关闭安全校验的建议，必须标注风险并建议人工确认；不自动执行。
- 日志脱敏：密码、token、cookie、内网 IP、数据库连接串不入库/不入日志。
- 输入限制：50KB/200 行；超限截断并提示，保留 Caused by 链和项目帧。

| 案例数据不足/偏科 | 只覆盖 Spring，其他分类效果差 | 覆盖矩阵；先补高频；报告分类指标 |
| 黄金集过拟合 | test 很好，holdout 差 | dev/test/holdout 隔离；holdout 不调参；盲测 |
| LLM 幻觉 | 根因看似合理但错误 | 证据引用；引用白名单；abstain；人工确认 |
| 检索不准 | 精确错误码/版本匹配差 | 指纹 + 全文 + 元数据过滤 + 重排 |
| 工单闭环太重 | 用户不愿确认 | 确认操作极简；一键“有效/无效”；后续自动化 |
| 范围膨胀 | 又去做通用问答/大屏 | 非目标清单；每个需求三问 |
| API 成本 | 评测/使用超预算 | 缓存；L1 不调 LLM；上下文裁剪；预算上限 |
| 实现与理解脱节 | 代码能跑，但讲不清设计取舍 | 垂直切片；每个文件逐行复述；第二个同类功能自己写 |
| 数据合规 | 公开案例版权/隐私 | 逐条整理；注明来源/许可证；脱敏；删除机制 |
| 演示环境不稳 | 隧道/服务挂掉 | 健康检查；降级；录屏备份；部署脚本 |

## 17. 面试讲述与拷打

> 以下按“项目完成后”的口径写。当前真实进度以第 15 章和 `AGENTS.md` 第 9 节为准，不要提前把目标说成已完成。

### 17.1 1 分钟版本

> 我做的是一个面向 Java 学习者的报错诊断系统，不是通用问答机器人。用户粘贴真实堆栈后，系统会抽取异常类型和堆栈帧、生成指纹，在自建的“报错—原因—修复—验证”案例库里做精确匹配和混合检索，再由大模型基于检索到的证据生成结构化诊断，并且必须带引用；没有证据时会明确说信息不足，而不是硬答。诊断结果会自动进入工单，由人工确认根因和修复是否有效；有效的工单会回流成新案例，无效的会成为负例。为了保证效果不是凭感觉，我建了 60 条黄金评测集，分 dev/test/holdout，CI 每次跑检索指标，夜间跑完整诊断指标。这个项目的护城河不是模型，而是案例数据、评测体系和工单闭环。

### 17.2 高频问题

**Q：为什么不做通用 Java 问答？**

A：通用问答已经被大模型覆盖，做出来容易被替代，也很难证明价值。报错诊断有具体输入、可验证结果、可沉淀数据，而且能嵌入工单流程；通用模型缺的是私有案例、版本上下文和可追溯证据，这正是项目要补的。

**Q：为什么用 RAG？是不是为了用而用？**

A：RAG 在这里只是“找证据”的手段。报错诊断需要引用历史案例，不能只靠模型记忆；但我们也设计了不用 RAG 的路径：指纹精确命中高质量案例时直接返回，信息不足时直接追问，没有证据时 abstain。RAG 不是产品，闭环和数据才是。

**Q：怎么证明你的系统有效？**

A：黄金集 60 条，分 dev/test/holdout；检索看 Recall@5/MRR，解析看异常类型准确率，诊断看根因准确率、引用正确率、答案忠实度、abstain 准确率；CI 分三层：PR 跑不调用 LLM 的检索层，夜间跑全量，发版跑 holdout + 人工抽检。所有指标带样本数和基线，不凭感觉。

**Q：怎么防止在评测集上过拟合？**

A：dev 调参、test 回归、holdout 只在发版跑；holdout 不参与 Prompt/权重调整；标签变更写 changelog；报告分类指标和失败样例；新增分布外用例。如果有人为了指标改标签，评审要拒绝。

**Q：AI 给出原因之后怎么办？**

A：自动创建诊断工单，但 AI 只给“待确认诊断”。人工确认根因和修复效果；有效 → 工单解决 → 生成案例草稿 → 审核入库；无效 → 驳回/升级。AI 不自动关闭工单、不自动改代码，因为报错受版本、环境和业务上下文影响，错误结论的代价高；人工确认同时是最有价值的标注信号。

**Q：为什么不用微调？**

A：知识会变、案例会增，微调更新成本高且难以引用来源；当前数据量也不足以支撑稳定微调。RAG + 结构化检索更适合“可更新、可追溯”的需求。未来如果有大量高质量标注，可以考虑微调来做格式/风格，但事实仍应来自检索。

**Q：检索为什么不用纯向量？**

A：报错里有大量精确信号：异常全限定名、错误码、SQLState、框架包名、版本号；纯向量容易把这些“看起来相似但实际不同”的案例混在一起。所以用指纹/全文做精确匹配，向量做语义补充，再加元数据过滤和 RRF 融合，最后规则重排。

**Q：怎么减少幻觉？**

A：四层：检索不到就 abstain；生成必须基于候选案例；引用做白名单校验；输出 schema 限制字段。再加人工确认和评测回归。不能靠一句“不要编造”解决。

**Q：Python 服务挂了怎么办？**

A：Java 先落工单，再调 Python；超时/异常时工单保留为 `DIAGNOSIS_FAILED`，返回明确提示，P1 用 MQ 重试。主站、工单、确认流程不受影响。FAISS 损坏可以从 MySQL 重建，重建期间降级为精确/全文检索。

**Q：这个项目最难的部分是什么？**

A：（按真实经历填写，候选）案例 schema 和质量控制、精确报错下的检索融合、评测标签与人工校准、工单闭环的确认体验。讲一个具体踩坑：现象 → 假设 → 验证 → 修复 → 指标变化，不要背概念。

**Q：如果给你更多时间/数据，下一步做什么？**

A：先扩案例覆盖和 holdout，再做重排模型/更好的指纹归一化，然后接 IDE/CI（报错发生时自动建单），最后才考虑通用问答。顺序不能反：先把诊断闭环做深。

### 17.3 面试时不要说的话

- “我的系统准确率 95%”——没有评测样本和基线，不要说。
- “用了 RAG 所以很先进”——RAG 不是价值本身。
- “AI 会自动修复”——当前设计明确不自动改代码。
- “用户量/并发很高”——没有真实数据，不要编。
- “这个很简单”——讲清取舍和失败路径，比堆名词更加分。
